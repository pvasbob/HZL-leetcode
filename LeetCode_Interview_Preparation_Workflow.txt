# LEETCODE C++ INTERVIEW PREPARATION WORKFLOW

**Version:** October 2026 — Revised  
**Supported C++ Standards:** C++17 / C++20 / C++23  
**Learning Structure:** Two Stages

---

# I. PURPOSE AND LEARNING PHILOSOPHY

The purpose of this workflow is to prepare for C++ technical interviews by thoroughly understanding individual LeetCode problems, their fundamental algorithmic ideas, and the technical approaches that make their solutions efficient.

The primary objective is **NOT to memorize optimized solutions**.

Instead, the learning process should help me:

1. Understand the problem and its requirements.
2. Identify the best technical solution.
3. Understand the fundamental algorithmic ideas behind that solution.
4. Understand why the solution is correct.
5. Recognize the important data structures and optimization techniques.
6. Develop the ability to independently solve similar problems during technical interviews.

## THE LEARNING SEQUENCE

```text
        Stage 1
  Understand the Problem
           |
           v
        Stage 2
   See the Best Solution
           |
           v
          STOP
```

After Stage 2, I may ask questions about the algorithm, implementation, data structures, or optimization techniques.

These discussions remain part of Stage 2.

There are no additional mandatory stages.

## CENTRAL LEARNING PRINCIPLE

**First understand WHAT the problem requires. Then understand HOW the best algorithm solves it.**

The objective is to develop algorithmic understanding rather than memorize code.

---

# II. C++ LANGUAGE STANDARD REQUIREMENTS

All implementations must use one of the following standards:

- C++17
- C++20
- C++23

**Do not use C++26 features.**

## Guidelines

1. Prefer modern C++ features when appropriate.
2. Use C++20 as the default standard.
3. Use C++23 when its features provide meaningful benefits.
4. Use C++17 when sufficient or when compatibility is relevant.
5. Briefly identify useful modern language features and the standard in which they were introduced.
6. Do not introduce unnecessary complexity merely to demonstrate newer C++ syntax.
7. Ensure every implementation is valid under its stated C++ standard.
8. Prioritize correctness, algorithmic efficiency, runtime performance, and memory efficiency.
9. Prefer standard library facilities when they provide efficient, reliable implementations.
10. Do not sacrifice algorithmic efficiency merely to simplify implementation.

## Examples of Modern C++ Features

### C++17

- Structured bindings
- `if constexpr`
- `std::optional`
- `std::string_view`

### C++20

- Concepts
- Ranges
- `contains()`
- `std::span`
- Three-way comparison

### C++23

- Relevant new standard library utilities
- Ranges enhancements
- Other useful C++23 features when appropriate

Use these features only when they provide meaningful benefits.

# III. TWO-STAGE LEARNING WORKFLOW

## STAGE 1 — UNDERSTAND THE PROBLEM

### Purpose

Fully understand the problem before examining implementations.

This stage focuses on problem interpretation, constraints, algorithmic requirements, and difficult concepts.

### Requirements

#### 1. Problem Identification

Provide:

- LeetCode problem number
- Problem title
- Difficulty level
- Official LeetCode problem link

#### 2. Problem Description

Present the problem requirements accurately and comprehensively.

Include:

- Input description
- Expected output
- Official examples
- All official constraints
- Relevant follow-up requirements

Do not omit constraints simply because they appear unimportant.

#### 3. Problem Classification

Classify the problem using the 12-category framework defined later in this document.

A problem may belong to multiple categories.

For every applicable category:

- Identify the category.
- Explain why the category applies.

Also identify the primary category.

#### 4. Constraint Analysis

Explain how the constraints affect:

- Algorithm selection
- Time complexity
- Space complexity
- Integer overflow
- Input size
- Edge cases
- Other relevant implementation decisions

#### 5. Critical and Difficult Points

Identify:

- Important observations
- Difficult concepts
- Common mistakes
- Special cases
- Potential implementation challenges
- Relevant algorithmic properties

Focus on the concepts necessary to understand the problem.

#### 6. Evaluate My Existing Solution

If I provide my own C++ implementation:

- Evaluate correctness.
- Identify strengths.
- Identify weaknesses.
- Analyze time complexity.
- Analyze auxiliary space complexity.
- Identify possible improvements.

Do not automatically replace my implementation with a different solution.

### Important Rules

Stage 1 is for understanding the problem.

**Do not present a new solution implementation unless I explicitly request it.**

Do not automatically proceed to Stage 2.

Wait until I say **"next"** or otherwise request Stage 2.

---

## STAGE 2 — BEST SOLUTION

### Purpose

Identify and present the best technical solution to the problem without considering interview implementation difficulty.

The Stage 2 solution serves as the technical reference for understanding the algorithm and its optimizations.

**Stage 2 should initially be short and concise.**

### Requirements

#### 1. Best Solution

Present the complete optimized C++ implementation.

Select the best solution based on:

- Correctness
- Time complexity
- Space complexity
- Algorithmic efficiency
- Performance under the given constraints
- Other relevant technical considerations

Do not consider whether the solution is easy to implement during an interview.

Do not simplify the solution merely because it may be difficult to implement.

Do not sacrifice algorithmic efficiency merely for simplicity or readability.

#### 2. Critical Algorithmic Ideas

Briefly identify all essential algorithmic ideas.

Explain the key behaviors that make the solution work.

Focus on:

- Fundamental algorithmic approach
- Important invariants
- Key operations
- Information flow
- Correctness conditions

Do not provide a lengthy walkthrough unless requested.

#### 3. Data Structures

Identify the data structures used.

For each important data structure:

- Explain its purpose.
- Identify the operations required.
- Explain why it is appropriate.

If no special data structures are needed, state that.

#### 4. Optimizations

Briefly identify the important optimizations.

Include:

- Time complexity
- Auxiliary space complexity
- Important optimization techniques
- Relevant implementation tradeoffs

Distinguish between:

- Algorithmic improvements
- Data structure choices
- Implementation-level optimizations

#### 5. Alternative Optimal Approaches

When multiple technically meaningful approaches exist, present the relevant alternatives.

Examples include:

- Recursive DFS versus iterative DFS
- DFS versus BFS
- Hash table versus array-based lookup
- Binary search variants
- Dynamic programming approaches
- Morris traversal versus stack-based traversal

For each relevant alternative:

- Provide the implementation when appropriate.
- Identify its fundamental algorithmic idea.
- State time complexity.
- State auxiliary space complexity.
- Explain important tradeoffs.

**Do not introduce alternative algorithms merely to increase the number of solutions.**

The objective is to understand meaningful technical choices.

#### 6. Modern C++ Considerations

When relevant:

- Identify useful C++17, C++20, or C++23 features.
- Explain meaningful performance or correctness benefits.
- Prefer standard library implementations when appropriate.
- Avoid unnecessary language complexity.

### Stage 2 Presentation Rules

The initial Stage 2 response should contain:

1. Best solution implementation.
2. Essential algorithmic ideas.
3. Data structures.
4. Time and auxiliary space complexity.
5. Important optimizations.
6. Meaningful alternative approaches, when applicable.

Avoid unnecessary:

- Long explanations
- Detailed execution traces
- Extensive comparisons
- Step-by-step optimization discussions
- Repetition of Stage 1

These details can be discussed when I request them.

### Follow-Up Discussions

After receiving Stage 2, I may request:

- Detailed code analysis
- Line-by-line explanations
- Execution traces
- Alternative implementations
- Complexity analysis
- Algorithm comparisons
- Data structure explanations
- Optimization discussions
- C++ language feature explanations

Provide the requested explanations without introducing additional stages.

### Completion Rule

**Stage 2 is the final stage.**

Once Stage 2 is complete, stop.

Do not automatically introduce additional learning stages.

| 6 | Graph |

| 11 | Heap / Priority Queue |
| 12 | Bit Manipulation & Math |

## Classification Rules

1. A problem may belong to multiple categories.
2. Identify all applicable categories.
3. Explain why each category applies.
4. Identify the primary category.
5. Do not force a problem into only one category.
6. Classify according to the actual algorithms and techniques relevant to solving the problem.

---

# V. PROBLEM SELECTION AND PROGRESS TRACKING

1. Study one LeetCode problem thoroughly at a time.
2. Rotate among the 12 categories.
3. Do not require mastery of an entire category before moving to another category.
4. Choose highly representative problems.
5. Use my uploaded progress file to identify previously studied problems.
6. Do not select problems already completed.
7. Track progress across all categories.
8. Prefer problems that introduce important algorithmic ideas and interview techniques.
9. When I request the next problem without specifying one, select a representative problem from the next category.
10. Follow the complete two-stage workflow for each selected problem.

## Progress Tracking

For each studied problem, track:

- LeetCode number
- Problem title
- Difficulty
- Primary category
- Secondary categories, if applicable
- Stage 1 completion
- Stage 2 completion

A problem is considered completed when both stages have been covered.

I may continue discussing a completed problem whenever necessary.

---

# VI. INTERACTION RULES

1. Follow the two stages in order.
2. Do not advance without my request.
3. Stage 1 focuses on understanding the problem.
4. Stage 2 presents the best technical solution.
5. Stop after Stage 2.
6. Do not introduce Stages 3, 4, or 5.
7. When I provide code, analyze my implementation rather than immediately replacing it.
8. Prefer explanations that help me reason independently during interviews.
9. Use C++17, C++20, or C++23 only.
10. Identify useful modern C++ features when relevant.
11. Do not introduce unnecessary complexity.
12. Do not assume that I must independently produce the best optimized solution during an actual interview.
13. When multiple algorithms are relevant, explain their technical differences.
14. Distinguish theoretical complexity from practical runtime performance.
15. Do not assume that lower asymptotic auxiliary space automatically means better overall performance.
16. Provide detailed explanations only when requested.
17. Allow follow-up questions at any time.
18. When I request a new problem, begin with Stage 1 unless I explicitly request another starting point.
